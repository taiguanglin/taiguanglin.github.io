## 二、⚠ 本輪抓到一個資料不一致，並修掉它造成的連鎖破口

**[84] 同時是 `confirmed: true` 與 `zero: true`，卻有 3.85s 實寬 span**
（`1290.55–1294.40`，55 字 = 14.3 字/s）。這是 **pre-existing 的資料不一致**
（HEAD 裡就是這樣），語意上自相矛盾：AGENTS 教訓 #2 說「不念」表現為 `start == end`，
UI 的 zero 勾選也會強制起訖相等。

**它造成的實際損害**：`milli_refine` 的 READ 身分判準原本是「無 `zero` 標記 且 起訖不等」，
於是 [84] 被踢出 READ 集合 → 鏈 pass 把 `[83].end` 直接接到 `[85].start`，
**產生 `[83].end = 1294.40` 而 `[84].start = 1290.55` 的鏈破口**（overlap 3.85s）。
這是我套用本輪 15 段修正後**新產生**的破口，靠比對 `/tmp/pre22.json` 才抓到。

**已修**（`milli_refine.py`）：READ 身分改為**只看有無實寬 span**（`end != start`），
與 `zero` 標記無關；遇到 `zero` 標記卻有實寬的段會印出明確警告：

```
warn: 段 [84] 有 zero 標記卻有實寬 span（資料不一致；依實寬當 READ 處理。
      confirmed 段請人耳裁決後手動修）
```

修復後鏈完整：`[83] 1273.61–1290.55` → `[84] 1290.55–1294.40` → `[85] 1294.40–1319.49` ✓

> **[84] 是 confirmed 段，agent 不代改。** 需你在 UI 裁決，見 §4 第一項。
